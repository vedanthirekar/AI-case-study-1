Miraflores

A web app where a tax firm prepares, reviews and files its clients' returns. The demo client is the Okafor-Lindqvist household (2025, federal and California). These notes cover the idea and data model, the errors found in that return, and how I used AI.

Core idea and data model

Each number on a client's return is linked to the numbers it is calculated from and to the document field it came from. What people do (verify, change, approve, sign, file) is stored as a list of actions. The original data is never edited.

  • Tracing

    Every line links to the lines that feed it and to the exact field on the document.

  • Actions, not edits

    Who did what, when and why. Nothing is overwritten, so anything can be undone.

  • Sign-offs

    If anything a sign-off covered changes, it reopens and shows what changed.

  • Checks

    20 checks compare the return with the documents, IRS records and client answers.

  • Rules

    Who can approve, see SSNs or file is checked in one place.

  • Timeline

    Shows what happened and when across the season: documents arriving, actions taken, the filing and IRS letters.

Data model

The data is never edited. People's work is saved as separate records on top of it. Every screen is built from both, so all screens always agree.

Tradeoffs

  • No server database. Work is saved in the browser. A real version would save the same records on a server, and the rest of the app would stay the same. A database would also let many people read and write at the same time; today that only works across tabs in one browser.
  • No login. The people you can act as (preparer, reviewer, partner, client and others) come from the client data, and the rules change with the person you pick. In production, admins would manage logins and add new users.
  • Scope. I focused on building and delivering the features. The infrastructure can be added when moving to production.
  • Tax impact is an estimate. The tax engine that produced the return cannot be rerun here, so the app cannot recompute the exact tax after a fix. It multiplies the dollar change by the per-dollar tax rates the data provides. This is what lets the app rank issues and apply the partner's $1,000 limit. A real version would rerun the engine.
  • Hiding SSNs happens in the browser. In production the server would mask them, so full numbers never leave it for people without clearance. Every reveal is already logged.

How I used AI

AI was used in two places: to build the app, and inside the app as an assistant (Mira).

Building it with Claude Code

  1. Learned the basics. I first got a working understanding of what a tax workpaper is, who uses it, and how a return moves from documents to review to filing.
  2. Brainstormed the display. I explored with AI the different ways a workpaper could be shown, and chose the graph: the return as a map you can click into, down to the source document.
  3. Described the flow. I described how the app should work, from the client list to the return map, review and filing. Claude Code built the plan around that.
  4. Checked the plan. I reviewed the plan against the brief before any code was written.
  5. Code. Claude Code wrote the code.
  6. Verified the code. I had it walk me through how the files connect and how data flows through them, so I could check the code did what the plan said.
  7. Fixed bugs. I tested the app myself and fixed the bugs I found with AI's help.

My decisions

  • Tradeoffs: what to simplify to build it in 1 to 2 days.
  • What each screen shows, starting from the firm's view: a client list, then each client's file.
  • Simpler screens, rebuilt around the return map after the first version felt too busy.
  • Adding Mira and choosing its model.
  • The wording a first-time visitor sees.

Checks:

  • Numbers: scripts rechecked every issue against the printed documents and the engine's tax rates.
  • Features: a 27-step test covers every requirement in the brief. It passed in Edge, Chrome and Firefox and on the live site.
  • Data: the data packet is byte-for-byte the same as delivered. The app only reads it.

Mira

An assistant that answers questions about a client's file, for example "how was the AGI calculated?" or "what is left before filing?". A return has hundreds of lines and dozens of documents. Mira saves reviewers from hunting for an answer, helps a new hire find their way on day one, and could later answer clients' own questions about their return.

  • Finding answers. Today it looks things up directly in the client's data. In production, with many clients and years, the data would live in a graph database (lines, documents and people as connected points), with a vector index for searching letters, notes and messages.
  • Sources. Every answer links to the numbers and documents it used, so a reviewer can check it in one click.
  • Safety. It is read-only, does no tax math of its own, and sees SSNs and bank numbers hidden. In production it would only see what the person asking is allowed to see.
  • Model and limits. It runs on a free model (NVIDIA Nemotron 3 Super), so answers take 20 to 50 seconds and can sometimes cite the wrong document. In production a paid model under the firm's privacy terms would be faster and more accurate.
Dollar figures are estimates based on the tax engine's rates for this return.
